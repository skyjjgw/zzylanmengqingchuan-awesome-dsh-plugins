# 筛选与核验标准

## 1. 这个仓库不做什么

本仓库不试图成为：

- GitHub `dsh-plugin` topic 的镜像；
- npm 包数量排行榜；
- 官方安全背书；
- “装上就一定能用”的承诺列表。

已有大型目录适合发现项目；本仓库只保留一批值得先读的项目，并把不确定性写出来。

## 2. 收录门槛

一个项目进入“精选”至少需要满足：

1. 有可访问的原始仓库或官方来源；
2. 能说清它解决的具体工作流问题；
3. 有 README、package manifest 或安装文档等一手证据；
4. 有明确的许可证，或明确标记许可证未知；
5. 能写出安装命令和至少一个已知限制；
6. 不把社区传言、搜索摘要或榜单排名当作功能证明。

## 3. 推荐等级

### ✅ 本机已安装并使用过

有真实本机 profile 中的安装或使用证据。这个等级只说明“在某个环境中发生过”，不能外推到所有 DSH 版本、桌面客户端或操作系统。

### 🧪 本机安装/配置

插件曾出现在本机配置，但没有完整记录端到端功能验收。不要写成“已经实测全部功能”。

### 📖 源码/README 核验

维护者读取了原始 README、manifest、安装说明或关键源码，但还没有在本仓库维护环境中完成安装冒烟。

### 👀 观察名单

方向有价值，但来源、维护状态、安装方式、兼容性或安全边界不足。观察名单不是推荐名单。

## 4. 每次复核要看什么

- 仓库是否仍然存在，主分支和 release/tag 是否正常；
- README 安装命令是否与 `package.json` / `dsh.bundle.patch` 一致；
- 是否声明许可证；
- 是否需要构建、Node.js、pnpm、系统命令或外部服务；
- 是否读取会话、工作区、凭据或写入额外目录；
- 是否存在重复 bundle、旧 patch、版本锁定或桌面端 profile 差异；
- README 是否说明已知限制和卸载方式；
- 对于 UI 插件，挂载点是否依赖不稳定的内部 DOM 契约；
- 对于模型/视觉/路由插件，是否区分文本模型、视觉模型、Provider 和账户额度。

## 5. 安全边界

第三方插件本质上是本地代码。读者安装前应：

1. 阅读源码、构建脚本和依赖；
2. 先在临时 `DSH_HOME` 或测试 profile 中安装；
3. 观察它读写哪些路径、是否启动子进程、是否发起网络请求；
4. 不把真实 API Key、Token 或私人会话直接放进 issue、PR 或截图；
5. 重要环境优先固定版本，并保留 profile 备份。

## 6. 复核日期

目录中的 `reviewed_on` 是“我们最后读取原始证据的日期”，不是作者最后发布的日期，也不是兼容性保证。DSH 处于 developer preview，兼容性可能随 runtime 变化。
